# 冻结集失败分析

基线：`npm run quality:frozen`，157 条样本（有答案 133 / 无答案 24）。
本文件记录 **2026-10-22 那一版代码** 的失败构成，改代码之后请重跑重写，不要沿用旧数字。

## 失败构成

| 类型 | 条数 | 占比 | 含义 |
|---|---|---|---|
| 空召回 | 56 | 78% | 该给答案却一条都没返回 |
| 有结果但排序错 | 11 | 15% | 召回到了，但正确条目不在 top-3 |
| 过期事实泄漏 | 3 | 4% | 被 superseded 的旧事实回到上下文 |
| 无答案却误召 | 2 | 3% | 语料里没答案，系统还是给了结果 |

结论很直接：**这不是排序问题，是召不回来的问题。** 调权重、调 top-K 都没用。

## 空召回为什么这么多

三个层次的原因，按影响从大到小：

### 1. 查询和语料只有单字重合

```
后端现在连的哪个库？     -> 「数据库统一使用 PostgreSQL 15」
```

查询里能成 2-gram 的只有「哪个」「个库」，语料里对应的是「数据库」。两边一个 2-gram 都不重合，
中文 2-gram 索引直接失效。换成「数据库用的什么」就能召回——但这个信息差恰恰是真实用户会有的。

### 2. 同义词表是查询侧单向的

查询说「口」，语料写「端口」；查询说「软件」，语料写「编辑器」。
现有扩展只把查询的词映射到别的词，**没法从查询里根本不存在的词出发**。
除非词表里恰好写了「口 → 端口」这条。

### 3. 覆盖率门槛对长查询偏严

`coverage = queryMatched / 原始 gram 总数`。一个 12 个 gram 的长查询只重合 1 个就是 0.083，
低于 0.1 的门槛。试过放宽到 0.05：召回率一动不动，无答案误召从 8.3% 涨到 12.5%，所以退回来了。

## 试过但不行的改法

记录在这里，免得以后重复试。

| 改法 | 结果 |
|---|---|
| 覆盖率门槛 0.1 → 0.05 | Recall 不变，无答案误召 8.3% → 12.5%，回滚 |
| 回退允许 queryMatched = 0（纯扩展命中） | 「服务跑在什么环境上」被「环境变量」骗去召回「数据库选型」，回滚 |
| 放宽 minMatched 2 → 1 | 未单独测，但同义词组里「环境」已经证明会撞车，风险同源 |

## 结论：目前还没有找到真正有效的修改

**当前代码的冻结集成绩就是 48.1%，没有任何一条修复留在主线上。**

这里必须写清楚，因为上一版文档把它写混了：

| 数字 | 来自哪个版本 | 现在还在吗 |
|---|---|---|
| Recall@1 48.1% / MRR 0.489 | 当前 master | **是**，这是基线 |
| Recall@1 57.9% / MRR 0.586 | 某个用 496 行同义词表的实验分支 | **否，已回滚** |

57.9% 那版被回滚，是因为它虽然把冻结集拉高了，却让开发集从 100% 掉到 88.9%：
词表里的「迁移」「环境」这类泛词散落在多个不相关条目里，把错误结果顶到了 top1。
所以它证明的是「词表覆盖面确实是瓶颈」，不是「这个改法可用」。

其余试过的改法（放宽覆盖率、回退放行更多条、只认固化记录）也全部回滚，
逐条数字见提交 c296fe1 的说明。

**这条实验记录本身也有价值**：它说明继续在词面匹配上调参，收益上限就在 50% 附近。
要再往上，得换机制（更细的分词粒度、实体/属性匹配，或者语义检索），
而不是再改一次 `minCoverage`。
