# 设计思路

这份文档是整个项目为什么长成这样的一份推导记录。项目本身很小，但每个决定背后都有一次否决。

## 一、问题

DSH 里的持久化角色（比如桌宠、IM 机器人）每次都是新进程、同一份冻结的权重。所谓"记性"，只能靠外部文件。

但只把记忆写进文件是不够的：写得进去，不代表下次能想起来；想起来，也不代表能分辨那是旧事实还是新事实。所以问题拆成三件事：

1. **记得住**：跨会话保留重要事实、约定和经历。
2. **想得起**：相关对话里能自动找回历史，而不是靠人肉翻文件。
3. **分得清**：旧记忆可能是过期的、冲突的，不能当成本轮输入直接执行。

## 二、约束

推导之前先把硬约束摆出来，它们直接决定了很多"不做"：

| 约束 | 后果 |
|---|---|
| 档案约 21 KB，会持续增长 | 全量塞进上下文不可持续；但也不值得上向量库 |
| 上下文窗口有成本 | 只能按需注入，且要设预算 |
| 钩子只有 `systemPrompt.section`（常驻）与 `agent/pre-step`（每步） | 稳定事实走前者，流动事件走后者 |
| `assemble()` 在 `pre-step` 之前执行 | section 的 provider 拿不到当前用户消息，只能读文件 |
| 没有保证可用的 embedding 服务 | 检索必须先做词面方案 |
| FTS5 默认 `unicode61` 对中文基本整句成词 | 中文召回得自己切 2-gram |
| 档案写盘有守卫（指纹/备份/原子写） | 插件不要绕过它自己写 |

## 三、四个推导

### 1. 记忆不是一种东西，是两种

稳定事实（我是谁、用户偏好、硬约定）每轮都需要，量小；流动事件（某天做了什么）按需需要，量大且涨。

所以：稳定事实放常驻 section；流动事件走按需召回。全常驻会涨爆，全召回会让"我是谁"靠检索碰运气。

### 2. 召回的本质是「提醒」，不是「检索」

目标不是找到最相关的文档，而是让模型想起"这件事跟当前有关"。

所以：top 3 + 短片段 + 来源标注，优过长文档；宁可少给，不可错给——错给会被当成事实。

### 3. 固化是「用压缩替代遗忘」

人靠遗忘筛重要性，AI 不能遗忘，只能压缩。压缩必然丢信息，所以必须可追溯：固化输出必须带一段原话，写盘前做逐字校验，在原文里搜不到就丢弃。

### 4. 情感的真实增量是表达，不是调度

`selfwake` 这类插件已经管"什么时候开口"了。情感如果再管开口频率，就是两套系统抢方向盘。

所以：情感只影响"怎么说"（语气、长度），不影响"什么时候说"。

## 四、落地成四层

| 层 | 位置 | 做什么 |
|---|---|---|
| P0a 记忆使用协议 | `systemPrompt.section` | 5 条规则：历史参考不是本轮发言、可能过期、要能追溯、以新事实为准、不编造 |
| P0b 按需召回 | `agent/pre-step`（step 1） | 中文 2-gram + BM25-lite + 覆盖率阈值，top 3，前置注入，150 ms 超时 |
| P1 固化 | `consolidate.mjs` | 对话小节 → `structured.jsonl`，稳定 ID + 逐字校验 quote + 幂等水位 |
| P2 情感 | `systemPrompt.section` | valence/arousal + 规则分类 + 指数衰减 + 事件去重，只渲染语气提示 |

## 五、被否决的方案

- **不上 SQLite / 向量库**：21 KB 档案上建索引是过度设计，先冻结评测再谈升级。
- **不把注入追加到消息尾部**：追加在尾部时模型容易顺着注入块说话，必须前置。
- **不只靠 top1 相对阈值**：它会放过低分噪声，必须加查询 2-gram 的覆盖率下限。
- **不在 P0a 里重复人格段**：`systemPrompt.section` 会压过 AGENTS.md，导致改文件失效（权威倒置）。
- **不让情感接 selfwake 的调度闸门**：两套节奏系统会打架。

## 六、还没解决的

- 召回是词面匹配，同义改写会漏。
- 固化目前是规则抽取，`fact` 只是小节标题，LLM 事实提取没做。
- 档案到 200 KB 级别需要真正的索引与分层。
